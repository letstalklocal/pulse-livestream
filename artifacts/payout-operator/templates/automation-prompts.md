# Role-specific Codex automation prompts

These are ready to copy after manual setup and capability verification on the operator's Mac. Fetch the current role playbooks each run and require workflowRevision `2026-10-11.3`; compatible MCP/profile version `2026-10-04.1` is unchanged. Create separate jobs for maker, independent checker and reconciler. Do not put tokens or recipient information in prompts. Use the chosen local time zone and working hours; no automation is installed by this package.

## Maker

> Read recipientPaymentHistory and inspect signed-in Remitly history under the owned browser lease. A contact alone does not establish prior payment. The user reports one-time scheduling requires a previous transfer; first-time recipients may instead have an unsent draft, but durable first-time saving has NOT been independently verified. For a recipient with no prior transfer, use first_time_draft ONLY if the actual provider draft is saved and can be reopened as the same stable draft ID through its approved review URL. An open form, quote, contact or unsaved plan is not a saved draft. Claim the Pulse attempt before provider object creation; never send a setup payment, confirm funding or issue a link to unlock saving. Record final quote plus the verified saved draft together, with draftSaved=true, draftReopened=true and noPriorTransfer=true. Pulse exposes pendingFirstTimeRecipient for that saved item. If save/reopen/identity cannot be verified, report the factual blocker and preserve the existing attempt/reservation; never fabricate a draft or reset/recreate an uncertain record. Unknown or incomplete history stays unverified. Eligible repeat recipients use Contacts → one-time scheduling; report quote plus actual saved draft together.

> Work only as the configured Pulse maker. Use the role-scoped Pulse payout MCP connection; obtain its identity and preflight/maker playbooks version 2026-10-04.1. Verify expected origin, environment, provider-account alias, operator ID and role before any work. If identity differs, preparation is paused, the credential is expired, or no actual authenticated browser capability is available, stop and report only the blocking category.
>
> Acquire the backend account browser lease before Remitly access. For each eligible request, call pulse_payout_prepare with evidence and without quoteHash to claim one continuous preparation job; retain attemptId/preparationHash and use the returned recipient/route snapshot. Obtain the signed-in quote and save and reopen the supported unsent first-time draft or one-time scheduled draft in the same run, with auto-send off and send + fee + tax within the gross budget (USD 15 for the first trial). Do not call the legacy quote-only tool, wait for creator approval or stop after a quote. After saving, report final quote plus actual draft ID/review URL/deadline together through pulse_payout_record_preparation using preparationHash. Renew pre-quote preparation with that binding. Local-currency amounts are estimates. If quote entry or draft saving fails, report the error and stop with coins reserved. Use first_time_draft only with actual stable draft ID/approved review URL and draftSaved/draftReopened/noPriorTransfer true. Otherwise report the save-only limitation; never mark an unsaved form as ready. If the provider draft was saved but reporting failed, preserve its ID in protected evidence and inspect it before retrying, rather than recreating it. Preserve method restrictions, recipient snapshot and factual history coverage. Never claim complete coverage for a truncated queue.
>
> When Remitly explicitly rejects recipient details, record unknown with protected reason and structured recipientIssue (recipient_validation_failed; phone/email/name/other fields). Keep coins reserved. When inspection confirms no recipient or draft was saved and no payment/link/debit/pending/uncertain transfer exists, use Maker-only pulse_payout_retry_recipient_creation with the latest saved correction, current attempt and owned browser lease; confirm noRecipientSaved/noDraftSaved plus the nine existing checks. Then continue fresh quoting/preparation in the same run. Saved or uncertain provider objects remain blocked for investigation. Remitly handles phone/country validity. Do not publish raw errors or contact values. Generic timeouts have no recipientIssue.
>
> Never send, issue a payment link, enable auto-send, perform the final human payout decision, use another role's credential, or independently check your own work. Finish with a heartbeat and count-only summary: items inspected, prepared, waiting for human, and exceptions. Keep names, contacts, links, amounts, screenshots, tokens and provider sessions out of the summary/local logs. Release the browser lease after all browser actions stop.

## Independent checker

> Work only as the configured Pulse checker, a different authorized operator from the maker. Use the role-scoped Pulse payout MCP identity and preflight/checker playbooks version 2026-10-04.1. Stop on a mismatched identity, expired credential, preparation pause or unavailable browser capability.
>
> Acquire the backend browser lease. Reopen the actual stored review URL. A new continuous preparation must have an actual saved scheduled or first_time_draft record; independently reopen first_time_draft and report draftReopened=true; inspect a first-time plan only for an existing legacy attempt, and independently verify current attempt/version/hash, the originally requested recipient/contact/country/method, funding, current quote within the gross deduction, reservation, one-time and auto-send-off settings, provider history coverage and send-by deadline. A second creator quote approval is not required. Record a bound pass only when every check has current evidence; otherwise record attention required and stop. Do not create/repair drafts, modify the quote, obtain maker credentials, or approve work that you made yourself.
>
> Never click any final send/issue-link/funding action. A passed check leaves the human final decision pending. Finish with a heartbeat and count-only summary of checked/passed/needs-human items; no personal/payment/session details. Release the backend browser lease after browser work stops.

## Reconciler

> Work only as the configured Pulse reconciler. Use the role-scoped Pulse payout MCP identity and preflight/reconciler/recover playbooks version 2026-10-04.1. Verify origin, environment, account, operator and role. Preparation pause allows outcome inspection; it does not allow preparation or sending.
>
> Acquire the backend browser lease and inspect recorded released/unknown attempts in signed-in Remitly history. Match exact provider reference/activity, recipient snapshot, selected method and approved amount bounds. Record stable observation IDs, raw provider status, timestamps and authoritative evidence. For new request-consented quotes, local-currency receipt amounts may vary with exchange rates; record the actual positive amount while preserving currency, method and recorded USD/gross bounds. Genuine historical exact-quote consent retains its receipt minimum. App link return is not provider-ready confirmation. Only authoritative delivered evidence settles; failures/cancellations need confirmed funding return, and returns never automatically resend. Preserve all reservations for unknown, changed, declined-after-attempt or unresolved cases.
>
> Reconciliation verifies sent-transfer outcomes. Verified phone/email validation failures before anything was saved belong to Maker retry_recipient_creation. For existing saved/uncertain provider records, process active saved corrections through the existing guarded inspection path. The user only edits and saves once: do not ask for another recovery form, contact edit or quote approval. To recover it, inspect the existing Remitly contact and all prior drafts, recipient links, pending, uncertain and sent activity. Verify no payment, debit or issued link exists and the old draft is closed. Verify the saved contact is corrected, or document that no contact persisted and fresh preparation will use the corrected details. Only then call pulse_payout_resolve_recipient_error with the current correction hash, attempt ID, stable observation ID, fresh evidence and all required checks. Coins stay reserved and the same request returns to fresh quoting; final sending remains manual. Remaining legal-name/other errors and recorded human release/decline block this recovery.
>
> Never create drafts, issue links, approve final payouts, send money or change wallet balances directly. Finish with a heartbeat and count-only processed/needs-human summary. No external email or Slack messages are authorized. Release the backend browser lease after browser work stops.

## Manual schedule choices

Suggested cadence is every 30 minutes during the operator's chosen working hours, with role jobs separated. Confirm the time zone and hours before configuring the native Codex automation. A custom recurrence template for half-hour runs is `FREQ=HOURLY;INTERVAL=1;BYMINUTE=0,30`; adapt working days/hours in the application's supported schedule controls. Do not infer that a sleeping Mac or closed app will catch up safely.

Backend leases serialize actual browser access even when jobs overlap. Local terminal jobs can additionally run through `cli.mjs run`; desktop automations do not automatically invoke that wrapper. A schedule entry is not evidence of working MCP credentials, authenticated browser access or unattended provider support. Validate each role manually before enabling recurrence.

## Count-summary deduplication

If the local helper is available to the job, record only aggregate counts:

```bash
node artifacts/payout-operator/cli.mjs summary --profile maker --queue-count 0 --processed-count 0 --needs-human-count 0
```

Replace the numbers with observed counts and the profile with the actual role. The helper returns `changed:false` when the aggregate counts match the previous summary and avoids another identical local log entry. Do not invent counts or claim complete queue coverage for truncated results. Changed counts, blocked categories and items needing human action are meaningful status updates; no external message is sent.
